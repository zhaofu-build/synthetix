## 二、能力分类与接入策略

### A 类：本地 FFmpeg 直接执行（无需 API 调用）

这些能力不依赖 core-nexus-ai，直接调用 FFmpeg 命令，**响应快、无网络延迟**：

```
剪切视频 · 合并视频 · 添加字幕 · 调整速度 · 视频压缩
视频转 GIF · 帧提取 · 音频添加 · 人声分离 · 降噪剪切
```

### B 类：通过 core-nexus-ai API 调用

这些需要调用 AI 服务，**有网络延迟和 token 成本**：

```
TTS 语音合成 · ASR 字幕提取 · 视觉理解 · 音乐生成 · LLM 文本生成 · 翻译
```

### C 类：第三方 API 调用

```
Pexels/Pixabay 视频搜索下载 · yt-dlp URL 下载
```

### D 类：基础系统工具

```
查询时间 · 列出目录 · 模糊查找文件 · 获取系统信息
```

## 三、Skills vs MCP 对比分析

### 方案对比

| 维度 | Skills（项目内注册） | MCP（外部协议） |
|------|---------------------|----------------|
| **实现方式** | `@registry.register()` 注册工具函数 | 启动 MCP Server 进程，暴露工具 |
| **适用场景** | 本地 FFmpeg、项目内服务 | 外部第三方 API、跨项目复用 |
| **延迟** | 直接函数调用，零开销 | 进程间通信 + JSON-RPC，有延迟 |
| **开发复杂度** | 低 — 写一个 async def 即可 | 高 — 需要独立的 MCP Server 项目 |
| **维护成本** | 低 — 跟项目代码一起 | 高 — 独立部署和版本管理 |
| **当前架构匹配** | ✅ 完美匹配现有 ToolRegistry | ❌ 需要新增 MCP Client 层 |
| **外部集成** | 不支持动态发现新工具 | ✅ 支持动态发现和热插拔 |
| **当前外部服务数** | 1 个（core-nexus-ai） | MCP 适合 3+ 个外部服务 |

### 建议：**Skills 为主，MCP 为备用**

**理由：**

1. **项目只有一个外部 AI 服务**（core-nexus-ai），已有 `CoreNexusClient` 统一封装，不需要 MCP 的动态发现
2. **大部分能力是本地 FFmpeg**，直接函数调用最高效
3. **现有架构已成熟**：`ToolRegistry` + `@registry.register()` + `IntentRecognizer` 完整闭环
4. **MCP 适合未来扩展**：当需要接入 3+ 个外部服务（如 Pexels API、字幕生成服务、素材管理平台等）时再引入

**如果未来需要接入的服务变多（比如 Pexels、Pixabay、Runway、Stable Diffusion 等），那时再引入 MCP 做统一外部工具管理。**

### 4.2 关于 FFmpeg 是否可以脱离接口直接调用

**可以。** 当前项目中所有 FFmpeg 操作已经是直接本地调用，不经过 core-nexus-ai：

```
ffmpeg_adapter.py → subprocess.run(['ffmpeg', ...]) → 直接执行 FFmpeg 二进制
```

以下操作全部是本地 FFmpeg 直接执行，**无网络依赖**：
- 剪切/合并/压缩视频
- 添加字幕（硬/软字幕）
- 调整速度/音量/分辨率
- 帧提取/GIF 转换
- 音频合并/人声分离

作为 Agent 工具注册后，用户说"帮我把前30秒剪出来"，链路是：

```
用户输入 → 意图识别(cut_video) → 槽位填充 → 确认 → tool_cut_video() → FFmpeg 本地执行 → 返回结果
```
